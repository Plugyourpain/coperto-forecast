# Architecture — Coperto Forecast

## 1. Goal
Прогноз числа гостей по ресторану на 7 дней вперёд.
Вход: история + (date, restaurant_id). Выход: 7-дневный прогноз + метрики качества.

## 2. Data
- Синтетический дневной ряд, 18 месяцев, 2 ресторана (генерируется скриптом).
- Схема: date (datetime64), restaurant_id (int64), guests (int64), revenue (float64).
- Паттерны: тренд, недельная и годовая сезонность, праздничные всплески, шум.
- Три РАЗНЫХ типа пропусков (обрабатываются по-разному):
  1. Закрытый день  → guests = 0, revenue = 0 (легитимный ноль).
  2. Сбой выгрузки   → NaN в guests/revenue (импутация, не dropna).
  3. Точки нет в выгрузке → строки отсутствуют (восстанавливаем календарь).
- Аномалии: один технический выброс (POS-баг) — обрабатывается явно.
  Новогодняя ночь — НЕ выброс, а событие, остаётся.

notebooks/
  01_eda.ipynb
  02_modeling.ipynb

## 4. Anti-leakage rules (жёсткие)
- Все лаги и rolling — со сдвигом (shift ≥ 1).
- Split только по времени, без shuffle.
- Imputer/Scaler/Encoder обучаются ТОЛЬКО на train (через Pipeline).
- Признаки на инференсе считаются той же функцией, что и на обучении.

## 5. Reproducibility
- random_state зафиксирован во всех моделях и в генераторе данных.
- requirements.txt с пиннингом версий.
- Скрипт обучения: python -m src.model --train (создаёт models/model.pkl).
- predict.py загружает модель, не переобучает.

## 6. Data preparation (src/data.py)

Три типа пропусков обрабатываются раздельно:

| Случай | Признак в данных | Решение | Флаг |
|---|---|---|---|
| Закрытый день | guests=0, revenue=0 | оставить как 0 | — |
| Сбой выгрузки | строка есть, guests=NaN | ffill по точке | `was_nan` |
| Точки нет в выгрузке | строки нет в raw | восстановить календарь + ffill | `was_missing_row` |
| Аномалия (POS-баг) | guests > 5×медиана | → NaN, затем ffill | `is_anomaly` |

Импутация — только forward-fill, без заглядывания в будущее.
Первые строки, где ffill не сработал, отбрасываются: без лагов бесполезны.

Флаги:
- `was_nan`        — исходное значение отсутствовало в raw (сбой выгрузки), импутировано ffill
- `was_missing_row` — строки не было в raw (точки нет в выгрузке), календарь восстановлен
- `is_anomaly`     — guests > 5×медиана по точке (POS-баг), заменено на ffill

Известное ограничение: восстановленные строки для регулярно закрытых дней
(например, понедельники ресторана 2) не распознаются как закрытые — ffill
даёт им ненулевую посещаемость. Детекция паттерна "каждый N-й день = 0"
оставлена как улучшение.

## 7. Features (src/features.py)

Единая функция `make_features(df, target, horizon=7)` вызывается и при
обучении, и при инференсе — это архитектурное требование ТЗ.

Признаки:
- Календарь: `dow`, `month`, `is_weekend`, `is_holiday` (RU_HOLIDAYS).
- Лаги: `lag_7`, `lag_14`, `lag_21`.
- Скользящие: `roll_mean_{7,28}`, `roll_std_{7,28}` — считаются после
  `shift(horizon)`.

Принцип anti-leakage: **все** лаги и rolling сдвинуты минимум на `horizon`
дней. Горизонт прогноза = 7, поэтому минимальный лаг тоже 7. Это отход
от типового примера (там `LAGS=(1,7,14)`), но позволяет обучать один
модельный объект без рекурсии и без риска утечки. Явно зафиксировано в
README как принятое решение.

Группировка: лаги и rolling считаются внутри `restaurant_id` через
`groupby.transform`, чтобы значения не перетекали между точками.

`revenue` исключён из признаков: он известен только для прошлого и
коррелирует с таргетом, что даёт частичную утечку целевой переменной.

Покрытие тестами (`tests/test_features.py`):
- лаг соответствует `shift`,
- изменение дня D не влияет на признаки < D,
- изменение дня D не влияет на признаки в (D, D+horizon),
- изменение дня D влияет на признаки в D+horizon,
- нет утечки между ресторанами,
- календарные признаки корректны.

## 8. Validation (src/validation.py)

- `time_split(df, valid_weeks=6)` — последние 6 недель в holdout,
  ничего не перемешивается. Граница строгая: train ≤ cutoff, valid > cutoff.
- Метрики: MAE (по всем точкам) и MAPE (нули исключены, число исключённых
  сообщается явно — при guests=0 метрика не определена).
- `naive_baseline_predictions` — `groupby(restaurant_id).shift(7)`.
  Это тот же день недели неделю назад, требование ТЗ.
- `compare(model_metrics, baseline_metrics)` — таблица для README с
  абсолютным и относительным приростом MAE/MAPE.
- `per_restaurant_metrics` — метрики в разрезе точек (для README и EDA).

Почему MAE и MAPE: MAE — интерпретируемая единица («ошибаемся на N гостей»),
её удобно перевести в бизнес-эффект (смены, закупки). MAPE — нормированная
ошибка, позволяет сравнивать рестораны с разным масштабом. Обе метрики
считаются на одном и том же holdout и для модели, и для бейзлайна.

## 9. Model (src/model.py)

- `build_linear_pipeline`: SimpleImputer(median) → StandardScaler → Ridge(α=1.0).
  Ridge детерминирован, random_state ему не нужен.
- `_try_build_boosting_pipeline`: LightGBM (если установлен). Деревья без scaler.
- `train`: prepare → make_features → time_split → fit кандидатов → выбор лучшего по MAE.
  Модель и feature_cols сохраняются в `models/model.pkl` (joblib),
  метрики и конфиг — в `models/metrics.json`.
- `load`: загрузка bundle, понятная ошибка если файла нет.
- `predict_for_dates`: без рекурсии, через append пустых строк + make_features.

Порядок операций при обучении (важно для отсутствия утечек):
1. prepare() — очистка, импутация, восстановление календаря;
2. make_features() — лаги/rolling на ПОЛНОМ ряду;
3. time_split() — режем готовые фичи по времени;
4. dropna только в train (первые дни ряда без истории);
5. Pipeline.fit на train → трансформеры настраиваются только на train;
6. predict на valid, метрики, сравнение с бейзлайном.

Бейзлайн считается на полном featurized-ряду, а затем срезается по
индексам валидации. Это гарантирует, что lag_7 первых дней валидации
опирается на train, и метрика не «теряет» точки. Модель и бейзлайн
сравниваются на идентичном множестве строк (84 точки).

## 10. Inference (predict.py)

CLI: `python predict.py --date YYYY-MM-DD --restaurant N [--days 7] [--out path.csv]`

Поведение:
1. Загружает сохранённый bundle (не переобучает).
2. Проверяет, что --days совпадает с горизонтом обученной модели.
3. Загружает и очищает историю через src.data.prepare (тот же пайплайн, что при обучении).
4. Проверяет, что запрошенный ресторан есть в истории.
5. Проверяет, что дата прогноза > последней даты истории.
6. Строит признаки через make_features (та же функция, что при обучении).
7. Возвращает CSV или таблицу в stdout.

Коды выхода: 0 — успех, 1 — ошибка данных/модели, 2 — ошибка аргументов.
Все ошибки — понятный текст в stderr, без трейсбеков pandas.

## 11. EDA findings → feature choices

Что показал EDA (notebooks/01_eda.ipynb) и как это повлияло на код:

| Наблюдение | Следствие в коде |
|---|---|
| Недельная сезонность — главный сигнал (пик Пт-Сб, ×1.4 к Пн) | признак `dow`, `is_weekend` |
| У ресторана 2 понедельник = 0 (санитарный день) | флаг не вводим; линейная модель физически не даёт 0 — зафиксировано в README как ограничение |
| 31.12 = ×2.3 от медианы, остальные праздники ×1.0–1.4 | `RU_HOLIDAYS` + `is_holiday` |
| POS-баг 12.11.2024 = ×13 от медианы | флаг `is_anomaly`, замена на `ffill` (не удаление) |
| Три типа пропусков (0 / NaN / нет строки) | раздельная обработка с флагами `was_nan`, `was_missing_row` |
| `revenue` коррелирует с `guests` r ≈ 0.96, но не строго | `revenue` не входит в `feature_columns` |
| Тренд положительный, годовая сезонность слабее недельной | `month` + лаги 7/14/21 достаточно; тренд улавливается через `roll_mean` |
| Худший день — вторник, а не понедельник | зафиксировано в ноутбуке: лаги хорошо справляются с закрытыми Пн; проблема в резких переходах профиля |
