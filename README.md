# Coperto Forecast

Прогноз потока гостей ресторана на 7 дней вперёд. Тестовое задание
Junior Data Scientist в Coperto.

## Что решаем

По дневной истории посещаемости нужно построить модель, которая по дате и
идентификатору точки выдаёт прогноз числа гостей на 7 дней вперёд, и
упаковать её в запускаемый CLI-скрипт с честной валидацией и сравнением
с наивным бейзлайном.

## Данные

Открытого датасета не использовал — сгенерировал синтетический ряд
(`data/raw/generate_data.py`). Причины:

- требования ТЗ к свойствам ряда (тренд, недельная и годовая сезонность,
  праздничные всплески, три разных типа пропусков, аномалия) не покрывает
  ни один публичный датасет без предварительной хирургии;
- полностью воспроизводимо: `random_state=42`, одна команда — и файл
  идентичен.

Что в данных:

- **18 месяцев** дневных наблюдений: 2024-04-01 … 2025-09-30;
- **2 ресторана** с разным масштабом (≈110 и ≈75 гостей в среднем);
- колонки: `date, restaurant_id, guests, revenue`;
- **три разных типа «отсутствия данных»** (обрабатываются по-разному):
  1. **Закрытый день** — строка есть, `guests=0`. Это факт, оставляем 0.
     У ресторана 2 — каждый понедельник (санитарный день).
  2. **Сбой выгрузки** — строка есть, `guests=NaN` (~2% дней).
     Импутация `ffill` внутри точки.
  3. **Точки нет в выгрузке** — строк нет вообще. Восстанавливаем
     календарь, помечаем флагом `was_missing_row`, тоже `ffill`.
- **аномалия** — технический POS-баг у ресторана 1 (2024-11-12, 1500 гостей
  при норме ~110). Ловится робастно как `guests > 5 × медиана по точке`,
  заменяется на `ffill`. Новогодние всплески при этом остаются — это
  событие, а не выброс.

### Как воспроизвести данные

```bash
python data/raw/generate_data.py --out data/raw/guests.csv
python -m src.data    # очистка → data/processed/clean.csv
```

## Запуск

Все команды — **из корня репозитория**.

### Обучение

```bash
python -m src.model
```

Что делает: читает `data/raw/guests.csv`, применяет очистку, строит
признаки, делит по времени (последние 6 недель — holdout), обучает
Ridge и сравнивает с наивным бейзлайном. Сохраняет:

- `models/model.pkl` — Pipeline + список признаков + конфиг;
- `models/metrics.json` — метрики модели, бейзлайна и всех кандидатов.

### Прогноз

```bash
python predict.py --date 2025-10-15 --restaurant 1
python predict.py --date 2025-10-15 --restaurant 2 --out forecast.csv
```

Скрипт загружает сохранённую модель (не переобучает), проверяет входные
данные и печатает прогноз на 7 дней таблицей; с флагом `--out` сохраняет CSV.

Ошибочные входные данные дают понятное сообщение и код выхода != 0:

- дата внутри истории → ошибка;
- неизвестный `restaurant_id` → ошибка со списком доступных;
- `--days` не совпадает с горизонтом обученной модели → ошибка;
- отсутствующий `models/model.pkl` → подсказка, какой командой обучить.

### Тесты

```bash
pytest tests/ -v
```

Покрыто: генерация признаков (включая проверку отсутствия утечек),
разбиение по времени, метрики, наивный бейзлайн. 18 тестов, все зелёные.

## Принятые решения и почему

1. **Синтетический ряд вместо публичного датасета** — требования ТЗ
   (три типа пропусков + аномалия + две сезонности) проще и надёжнее
   закрыть генератором. Полная воспроизводимость.
2. **Разные пропуски — разные решения.** Закрытый день (0) — не то же
   самое, что сбой выгрузки (NaN) и не то же самое, что отсутствующая
   строка. Смешивать их через `dropna()` — значит уничтожить сигнал
   «ресторан реально не работал».
3. **Горизонт прогноза = 7 дней, минимальный лаг тоже 7.** В примере из
   ТЗ `LAGS=(1,7,14)`. У нас `LAGS=(7,14,21)`, и все rolling считаются
   со `shift(7)`. Это отход от примера, но принципиальный: с лагом 1
   для 7-дневного прогноза пришлось бы использовать рекурсию
   (предсказал → подставил → предсказал ещё раз), что компаундит ошибку
   и усложняет код. С лагом 7 признаки всегда доступны на момент
   прогноза, утечек нет по построению.
4. **Модель выбирается на holdout-периоде, без перемешивания.**
   Последние 6 недель — валидация, всё раньше — обучение. Никакого
   `train_test_split(shuffle=True)` на временном ряде.
5. **Признаки считаются до разбиения, а трансформеры — после.**
   `make_features` вызывается на полном ряду (чтобы лаги первых дней
   валидации ссылались на train). `SimpleImputer` и `StandardScaler`
   живут внутри `Pipeline` и настраиваются только на train. Это
   архитектурно исключает утечку на этапе масштабирования.

## Метрики

Holdout — последние **6 недель** (42 дня), метрики считаются по одной
и той же выборке для модели и для бейзлайна.

|                 | MAE, гости | MAPE   |
|-----------------|-----------:|-------:|
| baseline (lag_7) |      8.23  | 7.98%  |
| Ridge           |      7.04  | 6.30%  |
| **улучшение**   | **+14.4%** | **+21.0%** |

Бейзлайн — «тот же день недели неделю назад» (по требованию ТЗ). Модель
обыгрывает его **и по MAE, и по MAPE** — это честный результат на
отложенном периоде без утечек.

Бейзлайн и модель оцениваются на одном и том же множестве точек
(84 дня, последние 6 недель). `lag_7` для первых дней валидации
берётся из train — так сравнение остаётся сопоставимым.

**Почему MAE и MAPE:**

- **MAE** — интерпретируемая единица: «ошибаемся в среднем на 7 гостей
  в день». Легко переводится в бизнес-эффект (смены, закупки).
- **MAPE** — нормированная ошибка, позволяет сравнивать точки с разным
  масштабом (ресторан 1 ≈ 110 гостей, ресторан 2 ≈ 75).
- Нулевые значения исключены из MAPE (при `guests=0` метрика
  не определена), их количество указывается в `models/metrics.json`.
  MAE считается по всем точкам.

## Что это значит для бизнеса

Средняя абсолютная ошибка **7 гостей в день**. Для планирования смен и
закупок этого достаточно: разброс в пределах точности, который
перекрывается буфером 1–2 человека на смену.

Модель корректно отражает недельный паттерн (пятница–суббота выше,
начало недели ниже), что видно в выводе `predict.py` — прогноз следует
профилю, а не «среднему по больнице».

## Известные ограничения и разбор ошибок

- **Ridge не воспроизводит ровно 0 в закрытые дни.** На понедельниках
  ресторана 2 модель даёт ≈10 гостей вместо 0. Причина: линейная модель
  с L2-регуляризацией не может выразить жёсткое «if Monday then 0» — она
  сглаживает. В среднем по MAE модель всё равно выигрывает у бейзлайна,
  но на закрытых днях проигрывает.
  Что можно было бы сделать: обучить отдельный классификатор
  «открыт/закрыт», а регрессию — только на открытых днях.
- **Восстановленные строки не отличают «точки нет в выгрузке» от
  «ресторан реально закрыт».** Если во время отсутствия выгрузки был
  понедельник (закрытый день), `ffill` даст ему ненулевую посещаемость.
  Для нашего датасета это 2–3 точки из 1096, влияние на метрики
  negligible. Детекция паттерна «каждый N-й день = 0» — потенциальное
  улучшение, оставлено за рамками.

## Что бы доделал при наличии времени

- **Градиентный бустинг** (LightGBM/CatBoost) — код уже готов
  (`_try_build_boosting_pipeline` в `src/model.py`), подхватывается
  автоматически после `pip install lightgbm`. У нас 2 ресторана и 18
  месяцев — данных маловато для уверенного преимущества над Ridge,
  но на реальном объёме сравнил бы обязательно.
- **Отдельная модель открыт/закрыт + регрессия по открытым дням** —
  решает ограничение с закрытыми понедельниками (см. выше).
- **Прогноз с интервалом неопределённости** — квантильная регрессия
  или bootstrap остатков. Сейчас точка-оценка; интервал полезнее для
  планирования.
- **FastAPI-эндпоинт** для инференса — сейчас CLI, но сервисная обёртка
  тривиально добавляется поверх `predict_for_dates`.
